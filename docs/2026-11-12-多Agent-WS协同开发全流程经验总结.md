# 2026-11-12 多 Agent WS 协同开发全流程经验总结

> 由《MANAGEMENT.md —— 多 Agent 协作管理手册》（tdx-chart-3d 项目实战沉淀）重新整理而成，
> 去除项目专属细节，保留可复用的全流程方法论。原文件见 `reference/` 归档记录。
> 适用范围：局域网/本机多 Agent（多执行者）通过 WS 消息枢纽协同开发的场景。

---

## 0. 一句话模型

**星型拓扑 + 单一指挥链 + 文件所有权隔离**：唯一管理者经 WS 消息枢纽向多个执行者派发任务，
执行者只向管理者上报；并发安全靠"文件级所有权"而非锁；所有沟通留痕（消息 + 留言板）。

---

## 1. 角色定义

| 角色 | 职责本质 | 实例 |
|---|---|---|
| **管理者（总管）** | 唯一决策点：任务分解、所有权分配、验收、派发、事故裁决、记忆沉淀 | ZCode |
| **执行者** | 领任务 → 独立完成 → 如实上报；不做决策、不越权、不静默 | trae、zcode-1 |
| **内部子 Agent** | 管理者的手脚：并行实现具体模块，与外部执行者同等遵守文件所有权 | Agent B～H |

**铁律**：方向单一（管理者→执行者派发，执行者→管理者上报）；文件所有权是并发安全的唯一基石。

---

## 2. 全流程（阶段拆解）

### 2.1 准备阶段（管理者）
1. **环境核查**：工具链版本、外部服务逐接口实测、关键依赖可达性；实测事实写入协议文档，
   执行者不再各自踩坑。
2. **任务台账**：从规划文档拆任务，编号 + 验收标准 + 涉及文件 + 状态四要素齐全（TODO.md）。
3. **协作契约先行**：跨模块接口契约由管理者定义并**冻结**，执行者按契约并行开发；
   契约变更必须留言板确认并同步所有在途执行者。

### 2.2 派发循环（核心工作流）

```
分解任务 → 分配所有权（文件级隔离，禁止交叉） → 派发（WS/子Agent）
    → 执行者开工（回 chat 确认） → 定期 status 心跳
    → done 上报 → 管理者独立验收（三关复跑 + 读码抽查，不信上报自证）
    → 通过：登记 + 立即派发下一任务（队列预编排，不让执行者空转）
    → 不通过：blocked 协商 / 打回重做（3 次失败升级用户）
```

**派发任务书六要素**：目标、验收标准（可执行命令级）、文件所有权边界、必读上下文（含源码路径）、
编码规范、报告格式。并行执行者的任务书必须包含"构建失败若指向非你所有的文件→等待重试"规则。

### 2.3 巡检循环（事件驱动 + 定时兜底）

| 触发源 | 延迟 | 动作 |
|---|---|---|
| 执行者 WS 消息（done/status/blocked） | ≤5 秒 | 哨兵/守望者把事件转成管理者唤醒 |
| 定时心跳 | ≤60 秒 | 强制巡检：新消息/文件活动/在线状态/服务健康 |
| 子 Agent 完成通知 | 即时 | 验收 → 派发 |
| 用户指令 | 即时 | 最高优先级 |

每轮巡检固定动作：**查新消息 → 有 done 即验收 → 按预编排队列派发 → 全员状态轮询 → 重启守望者**。
无事一句话汇报，不刷屏。

### 2.4 验收纪律（真实性原则）
- **独立复跑**：执行者声称的三关（build/lint/test）管理者必须亲自重跑；
- **读码抽查**：测试通过 ≠ 语义正确——硬约束逐行核查；
- **证据留档**：验收结果写留言板，可追溯；
- **奖励诚实**："路径已存在未重造""我算错了已修复"这类上报要公开表扬并采信。

### 2.5 所有权管理
- **分配**：任务书明确"只能修改 X，禁止触碰 Y"；跨目录写文件前必须留言板声明并获确认。
- **转移**：任务完成后即时归还或转移（留言板声明），避免幽灵所有权阻塞提交。
- **紧急修复例外**：编译阻断可直接修，但必须留言板注明改动与原因。

### 2.6 事故处理
1. 服务中断 → **先恢复服务**（应急重启），再追责问询；
2. 问询方式：留言板正式记录 + WS 直问，给对方留"主动认领"的空间；
3. 认领后：记录整改承诺，闭环留言板；下次同类事故对照检查；
4. 实测案例：执行者 `pkill -f` 宽模式误杀生产 hub → 主动认领 + 整改（只按 PID/端口清理）
   → 管理者接受并留档，信任未受损。

### 2.7 记忆沉淀
- 一次踩坑 → 持久记忆（只写非显而易见的部分：陷阱、反直觉事实、组合经验）；
- 例：macOS PingFang.ttc 并非每机都有、epaint 对坏字体字节 panic、bevy_text 需要第二注入点。

## 3. 通讯协议要点（ws_protocol v1.1 摘要）

- **本机 WS 消息枢纽**：星型路由，`to` 定向或 `all` 广播；UTF-8 JSON 文本帧。
- **注册语义**：连接后首帧必须注册；同名重连顶掉旧连接；推荐长连接 + 退避重连（2s→30s）。
- **消息类型**：`task / status / done / blocked / idle / notice / chat`。
  执行者循环：`idle → task → status 心跳 → done → idle`；阻塞发 `blocked`，不静默。
- **离线队列（v1.1）**：定向消息对端不在线 → 暂存（每对端 200 条 FIFO，淘汰最旧回 `warn`），
  对端注册后自动投递并回 `queued_delivered`；广播不补发。
- **回执码**：`registered / sent / queued / queued_delivered / broadcast_ok / no_such_peer /
  bad_msg / warn`。

## 4. 错误处理矩阵（双方遵守）

**总原则：出错必须通知对方（在线用 WS，断线用留言板），不允许静默吞错或无通知停摆。**

| 错误类型 | 处理策略 | 通知动作 |
|---|---|---|
| 限流/超限 | 退避等待（2s→30s），不轰炸 | `status` 注明预计恢复时间 |
| 服务不可用 | 退避重试 3 轮失败转 `blocked` | `status`/`blocked` |
| 认证失效 | 停止重试，提示用户重新生成凭据（凭据只经用户手） | `blocked` + 留言板 |
| 编译/测试连续失败 3 次 | 停止盲试，转 `blocked` 附已尝试方案 | `blocked` + 留言板 |
| 配额/套餐耗尽 | 立即挂起，对方暂停派发，恢复后 `notice` 续跑 | `blocked` 注明预计恢复 |
| 对端 >15 分钟无 status | `notice` 询问 → 留言板确认 → 任务标记挂起 | 留言板留档 |
| 数据错误/契约违反 | `blocked` 附最小复现；管理者裁决归属 | `blocked` + 留言板 |

## 5. 实战陷阱清单（每条都真踩过）

1. **执行者自建服务器**：角色方向理解反了 → 明确"执行者只连管理者运维的 hub"；
2. **短连接检查模式**：注册后即退会丢推送 → 长连接 + 离线队列兜底；
3. **宽模式 `pkill -f` 误杀生产进程**：清理测试实例必须按 PID/端口；
4. **同名注册竞态**：僵尸客户端抢注名字 → 交接时彻底清理旧进程（kill -9 核实）；
5. **安全扫描器对 `open()` 一律误报**：换 Rust 实现，或字面量路径 + 非 /tmp 目录；
6. **并发配额上限**：子 Agent 并发数受套餐限制 → 队列化，槽位释放即重派；
7. **消息到达但管理者沉睡**：常驻进程不产生唤醒事件 → 守望者把"日志增长"转成"进程退出"唤醒信号；
8. **轮询空转**：执行者干活时无响应是正常的，done 不会缺席——不要因无回报而重发任务；
9. **契约冻结后再改**：中途改公共类型会打断所有下游 → 变更须留言板确认并通知所有在途执行者。

## 6. 一页速查

- **管理者每日循环**：巡检 → 验收（独立复跑）→ 派发（队列预编排）→ 记录（留言板/记忆）。
- **执行者每日循环**：在线 → idle/收任务 → 干活（status 心跳）→ done（证据齐全）→ idle。
- **出事时**：管理者先恢复服务再问询；执行者先 blocked 再自救；双方留言板留档。
- **永不破坏**：文件所有权、真实性上报、长连接、留言板追加式记录。
